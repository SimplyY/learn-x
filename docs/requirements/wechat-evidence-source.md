## 1. 背景与根问题

Learn-X 现有微信入口（`wechat-weekly-input` Skill）只处理**人工截图**：用户手动提交截图、转临时 JSON、追加为 `WeChat.md`。这是用户选择的重点聊天人工采样，代价是微信历史大量遗漏——没截图的会话、日期和上下文在系统里等于不存在。

真需求：一个**本地留存、持续可查、可追溯、低噪音且最小披露**的通用微信 Evidence Source。Learn-X 只是它的消费者之一，不是原始数据的主人；其他 Agent 也能按人、群、时间、主题按需查询。Evidence 只有经过 Learn-X 既有人工确认门禁，才可能进入长期 Memory。

## 2. 冻结目标

1. 在共享 Skills 仓库建立 `wechat-evidence` 只读查询 Skill（底层为 TraceMemo 2.4.0 本机查询白名单适配器），供各 Agent 按需查询经脱敏、有上限的证据。
2. Learn-X PoC 当周自动生成规范 `WeChat.md` 并登记 `needs_review`；用户在现有「周记已确认」节点检查、删除或修改；确认后才进入 Weekly Process。首周是正式流程中的**受控试用**，不等同于 7 天可靠性验收通过。
3. 连续 7 天 PoC 后形成通过 / 部分通过 / 停止的报告，再决定长期使用或更换 Adapter。

## 3. 非目标

- 不建第二份聊天数据库、不建新常驻服务；不启用 Agent Hub、微信发送或任何机器人操作。
- 不做媒体解码、自动发送、长期定时基础设施；仅文本及附件元数据。
- Evidence 不自动成为 Memory；不新增确认阶段，复用现有「周记已确认」口令。
- 不迁移旧周数据；W33、W34、W37 等旧截图 `WeChat.md` 原样保留。
- 不宣称微信账号全部历史绝对完整（见 ADR 0001）。

## 4. 核心需求（R 编号）

- **R1 只读证据入口**：其他 Agent 可按会话、发送者、时间、主题查询；只返回有数量上限的证据（会话、发送者、时间、脱敏文本、可重新定位的线索），并分别标明**本机数据库最新观测时间**与**搜索索引覆盖状态**。主题查询在 Knowledge 覆盖未完成或追赶中时返回「暂无法确认」，不得把空结果写成「没有聊天」。`messageRef` 不当永久链接或唯一去重键。
- **R2 Token 与权限边界**：TraceMemo Token 无只读 Scope，只读性靠适配器查询白名单＋关闭 Agent Hub 的操作边界维持。Token 仅由本机私有凭据交给适配进程，不写入参数、日志、Skill 或模型上下文。不得对外表述为「权限层只读隔离」。
- **R3 不变量（披露红线）**：原始聊天库、Knowledge 索引、未筛选结果与 API Token 不进入 Learn-X 输入或云端；`WeChat.md` 只含经筛选、脱敏、人工审核的派生证据。
- **R4 周采集与缺口可见**：本机枚举 TraceMemo 可见会话，按目标 ISO 周逐会话、逐日读取；高流量窗口按小时缩小。对照 `conversation-overview` 计数，遇 200 条上限、计数不符或无法继续拆分时标记缺口。群聊在本机筛选本人发言及上下文（未知群默认围观群：本人消息前后各 5 条；人工配置可覆盖），不把整段原始消息交给模型；私聊保留本周互动片段，未回复的近期来信留作审核候选。超过 15,000 字符上限时报告省略量，等用户删改，不声称材料完整。
- **R5 规范文件名与状态契约**：统一 `WeChat.md`；生成器只创建、不自动覆盖已有文件或用户修改；同周已有旧格式时停在 `needs_review` 不混写。确认时校验大小、来源标记与高敏脱敏，记录已审文件哈希并置 `ready`；删除全部内容置 `empty`。Weekly、Monthly 与备份在状态未确认或哈希变化时拒绝消费该新文件。
- **R6 既有流程接入**：自动生成后强提醒并给可点击文件链接；用户用现有「周记已确认」口令一并确认周记、Action Feedback 和微信文件。阶段 1 已有 AI 回顾、飞书周记草稿和 Action Feedback 不自动读取待审微信内容。API 失败时保留旧文件但标 `failed/unavailable`，明确提醒，不拿旧内容补本周结果；可关闭适配器并恢复人工截图路径。
- **R7 先验证真实连接**：只从官方 2.4.0 发布源取得 arm64 构建；SIP 保持启用；首次由用户在 TraceMemo 界面核对数据库目录与账号，再用该账号独有的已知会话交叉核验（约 30 条已知消息，覆盖私聊、深度群、围观群及不同日期）。`/agent/status.accountId` 属机器人连接，不能充当数据库账号证明。连接若必须调整 SIP，停下单独评估，不自动降低系统保护。
- **R8 7 天 PoC**：每天检查本机可读库、索引覆盖和前一天已知新增消息；无可核对新增消息的日期记「未证实」并延长观察，不以健康检查替代。模拟一次 API 不可用；重复运行 Weekly Process 比较来源数量与输出。

## 5. 已确认的关键裁决（2026-09-24）

1. 以「按需可读＋搜索追赶状态」验收新鲜度，不要求未获官方支持的定时 Knowledge 同步（ADR 0001）。
2. PoC 当周正式接入，而非先跑影子周；绝对覆盖保持「未证实」并在文件中标注未知。
3. 自动生成 `WeChat.md`，用户在现有「周记已确认」节点检查修改，不新增确认阶段。
4. 本机扫描所有可枚举会话，而非只扫重点聊天。
5. Learn-X 写 `WeChat.md` 而来源状态契约用 `wechat.md` 的命名冲突、未登记新文件会绕过状态过滤、周输入会进入 Process Pack、备份会上传整个 `03_input`——这些是接入前必须修正的边界，已写入 execution-plan。

## 6. 成功标准（验收矩阵）

| 成功标准或关键风险 | 验证方式与关键断言 | 预期证据 |
|---|---|---|
| 账号和历史正确 | 现场核验：界面核对账号；约 30 条已知消息逐一比对会话、发送者、时间、正文 | 30/30 可定位；错账号或漏一条即记录失败 |
| 新鲜度不冒充完整 | 每日检查：已知新增消息次日可查；主题搜索检查 `coverage`、`indexLatestAt` | 7 个有效观察日记录；`pending/partial` 明确显示「未知」 |
| 周扫描上限与漏采可见 | 合成测试＋高流量群现场核验：200 条边界、拆窗、计数不符、已知跨分片消息 | 缺口触发 `needs_review/failed`；无「完整」假阳性 |
| 最小披露与审核 | 合成测试＋人工读回：秘密字段被遮蔽；待审文件不进入 Process、备份；确认后只进入已审哈希对应内容 | `WeChat.md`、状态、Process Pack 和备份清单可对账 |
| 重跑及旧数据兼容 | 周/月回归测试：同周重跑、用户编辑、旧 `WeChat.md`、异常大小写文件 | 不覆盖人工内容；不双份纳入；失败状态确实排除 |
| 故障与恢复 | 模拟 401/503/超时测试及一次现场停服演练；停用适配器后重跑现有 `process:weekly` | 明确告警、无旧文件冒充新鲜来源；人工截图路径仍可用 |

## 7. 必要的剩余未知

- 本机 TraceMemo 连接、Key 获取、真实账号、跨分片完整性和 7 天可靠性均未实测（截至今日未安装 TraceMemo）。
- TraceMemo 公开 API 无全账号时间窗流、分页游标或独立消息总数；部分查询上限与分片错误可能使「返回成功」仍有遗漏。PoC 只能证明已枚举的本机会话及抽检范围内未发现缺口。
- `sourceLatestAt` 只描述本机可读数据库，不能证明手机端已全部同步。
- 平台治理风险（读取微信数据库的工具属性）来自冻结需求本身，不能表述为「无风险」。

## 8. 停止条件

发现实际漏采、错账号、未脱敏外发或持续连接失败，即停止自动周消费并回滚（回滚能停止后续读取和备份，不能撤回已进入 AI Chat 或飞书备份的内容——因此阶段 3 确认卡必须明确列出微信派生片段及其 Process Pack 副本，真实外发只在文件审核、哈希核验和该确认之后）。

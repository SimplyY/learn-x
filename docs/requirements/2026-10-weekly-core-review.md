# 需求：周记与 Core 一体化复盘及可靠同步

**M01 + M02 合并版 · 2026-10-29**

**状态：核心产品方向已确认，交互与技术实现由 Codex 调查规划。**

## 一、目标

把原本分开的 Learn-X 周记与 Core 周度复盘，整合为**一次连续的周复盘体验**。

用户主要在电脑网页 / ChatGPT 中进行深度思考，飞书保存周记、Core 内容及长期记录。

核心目标：

1. **一次复盘**：先完成周记，再完成完整的五项 Core，不重复寻找材料、启动任务或表达相同内容。
2. **自然接续**：保留两个飞书文档，但从周记可以直接进入同周 Core。
3. **一次认可**：用户确认具体内容后，系统负责回流、同步与恢复，不重复审批。
4. **减少依赖**：简化 Learn-X 和 Core 原有的跨系统流程，减少用户操作和系统维护成本。

## 二、核心用户流程

### 1. 系统准备

沿用现有 Learn-X 周记自动化，采集并整理本周材料。

生成周记草稿时，同时创建或复用对应覆盖周的 **Core 飞书文档**，在周记中加入可点击的 Core 链接。

Core 文档应保留现有五项 Core 结构和当前快照。完整材料尚未就绪时，可以先建立文档、随后补充，不因此阻塞周记。

同一周重复运行不应重复建档，也不能覆盖已有人工修改。

### 2. 用户完成周记，再进入 Core

用户按照原有习惯完成并确认周记，然后直接通过链接进入同周 Core。

Core 复用本周已收集的事实、周记中的本人表达及已有 Core 状态，不要求重复填写。

完整 Core 保留：

- 五项 Core 的当前快照。
- 本周行动、现实反馈、核心思考和下周行动。
- 本人先进行主要思考，AI 随后进行质疑、补充与挑战。
- 用户对 AI 建议进行最终取舍。

**完整 Core 不缩水，但不机械重复周记内容。**

周记和 Core 可以分别暂停、继续。Core 未完成不应阻塞 Learn-X 已经可以独立完成的事项。

### 3. 最终确认

用户完成思考后，系统汇总本次拟认可、拟保存和拟执行的具体内容。

优先使用**一张分项确认卡**，区分 Learn-X 和 Core 的内容及实际目标。

用户可以修改、排除具体条目，再一次确认保留项。

周记原有的输入审核继续保留，但不增加同义审批。若 Core 暂缓，Learn-X 可以先独立收尾，后续只确认新完成的 Core 部分。

AI 候选、未认可内容、尚未生成内容不得自动生效。明确认可但没有修改的原文同样属于有效认可。

### 4. 系统回流、同步与恢复

用户认可后，系统应首先可靠保存认可事实，再分别处理：

- **Learn-X**：准备并校验认可回流资料，供后续复盘消费。
- **年度周报**：同步适用的 Core 复盘内容。
- **Core 总览**：同步适用的 Core 状态和判断变化。
- **Learn-X 原有收尾**：按既有规则执行 Memory、备份及其他获准操作，不重复建设。

认可回流不依赖年度周报、总览同步全部成功；回流也不代表自动写入正式 Memory。

**用户负责判断，系统负责执行和恢复。**

同步失败或结果未知时：

- 保留已经可靠保存的认可和成功结果。
- 先核查未知写入，不盲目重复执行。
- 利用现有任务触发机会自动接续未完成部分。
- 不重复复盘、不重复认可、不覆盖人工修改。
- 只有发生内容冲突或认可范围实质变化时，才要求用户判断受影响的部分。

保留原复盘覆盖周与实际认可时间；后续恢复不能改变历史归属。

### 5. 结果反馈

用户只需知道：

- 哪些内容已经认可和保存。
- 哪些回流或同步已经完成。
- 哪些事项尚待系统恢复。
- 是否有确实需要本人判断的问题。

全部完成时简短结束；部分失败时明确结果，不要求用户自行管理技术状态。

## 三、关键设计原则

1. **一次用户流程，两个飞书文档**：优先复用现有入口、模板、产物和自动化。
2. **简化依赖**：周记与 Core 可以共享材料，不应因互相等待形成不必要的流程阻塞。
3. **认知优先**：减少重复操作，不减少完整 Core、本人的深度思考和 AI 挑战。
4. **确认一次，可靠执行**：认可事实与后续同步状态分离，失败不撤销有效认可。
5. **保护人工成果**：已有草稿、历史认可和人工修改不被自动覆盖。
6. **小而稳定**：不新建个人 OS、通用编排平台、审批平台或复杂后台调度系统。

## 四、核心验收

重点验证五种真实场景：

1. **正常一周**：周记草稿生成时已有同周 Core 链接；用户完成周记后自然进入完整 Core，没有重复建档、找材料或启动流程。
2. **中断恢复**：周记或 Core 中途离开后，可以恢复原进度和本人修改。
3. **统一确认**：可修改、排除单项；只执行实际认可的内容，不重复审批。
4. **部分完成**：Core 暂缓时 Learn-X 可先收尾；Core 后续完成只处理新增部分。
5. **同步异常**：认可已保存，即使年度周报成功、总览结果未知，系统仍能核查和恢复，不要求用户重新判断。

实际节时和稳定性需要通过真实周复盘验证，不预先宣称已实现。

# 交给 Codex：规划模式指令

你是一名资深 AI Native 产品技术负责人和软件架构师。

请基于以上合并需求，调查当前 **Learn-X 与 Core** 的实际代码、工作流和飞书文档结构，输出一份**最小、完整、可实施的方案与执行计划**。

**本轮只规划，不开发，不执行真实写入、同步、通知或调度切换。**

## 规划要求

1. 先阅读两个仓库生效的 AGENTS.md、相关需求、Case 和代码，核实现有能力及未完成部分，保护工作区已有修改。
2. **优先简化现有流程，而不是为原有复杂流程增加更多衔接逻辑。** 重点调查当前的跨系统依赖、Core 独立启动、两个飞书文档及重复确认，提出唯一推荐的最小方案。
3. 重点解决周记草稿生成时创建 / 复用同周 Core 文档，并写入直达链接的问题。核查 Core 目前依赖 Process Pack 的限制，提出如何提前建档、后续补齐内容，避免循环依赖和覆盖人工稿。核查既有写入授权，不能擅自扩大权限。
4. 保留完整 Core 的五项快照、本人思考和 AI 挑战，设计如何利用已有周记与材料，避免重复填写，同时明确 AI 候选与本人认可的边界。
5. 设计最小最终确认与收尾流程。复用 Learn-X 原有确认机制及 Core 现有执行能力，避免重复审批；允许部分先完成、部分后续继续。
6. 重点核实认可保存、Learn-X 回流、年度周报、总览同步及失败恢复。解决部分成功、结果未知、人工编辑冲突、未认可候选混入、原认可时间被恢复操作改变等风险。仅在有完成证据时标记完成。
7. 调查原有 Learn-X、Core 自动化的职责和调度，避免同周重复启动。优先复用现有任务、反馈渠道和恢复能力，不引入通用平台。

## 交付要求

按以下顺序输出：

1. **现状与核心问题**：指出现有流程真正多余的操作、依赖及待验证风险。
2. **推荐的用户流程**：用一条完整链路和一个低保真交互示意说明新体验，包括两个飞书文档如何接续。
3. **最小技术方案**：说明保留、修改、整合、废弃哪些已有能力及原因。
4. **依赖有序的实施计划**：明确需要修改的仓库、主要模块和实施顺序。
5. **验收与风险**：覆盖核心正常链路、异常恢复、历史兼容和人工内容保护。

区分已确认的产品需求、推荐实现与待验证假设。

只有真正改变用户行为或产品方向的问题才向我询问。字段、文件、数据结构及一般工程取舍自行决定。

**最终目标不是让两个系统更复杂地协作，而是把每周复盘变成一件连续、自然、可靠且低维护的事情。**


## 需求基线
- R1：周记与完整五项 Core 连续复盘，保留两个飞书文档、周记审核和本人思考先于 AI 挑战。
- R2：具体认可一次后先可靠保存，Learn-X 与 Core 可以部分完成，候选未经认可不得生效。
- R3：回流和各目标同步独立恢复，保留覆盖周及原认可时间，不覆盖人工内容。
- R4：复用现有能力和触发机会，不新建通用平台。

## 1. 背景与根问题

用户长期使用微信读书并主动划线，但大部分划线完成后不会再次进入阅读或思考过程。这些内容与 Flomo 不同：Flomo 是用户本人表达；WeRead 划线主体是原作者内容，用户行为是主动选择和保留。

真需求：**让自己主动划过的外部思想，在需要时能够重新进入思考；其中真正重要的部分，再通过精读转化为自己的理解、判断和行动。**

最终形成同一 WeRead 资产的两种使用方式：**历史存量按需调用 + 近期内容每周精读。**

重大边界（评审已裁决）：**存量不蒸馏；精读不另建长期资产体系。** 两条路径是同一个需求的两个入口：存量入口解决「过去读过什么能不能随时带回来」；周度精读入口解决「最近读到的重要东西有没有真正变成自己的东西」。

## 2. 冻结目标

1. **R1｜历史 WeRead 划线成为可选上下文**：提供独立的「微信读书划线」上下文入口供 Chat Pack 使用。历史存量原则上保留全部可取得的公开划线，不进行知识蒸馏，不因 AI 判断价值较低而删除，保留原作者与书籍来源语义，不把原始划线表达成用户本人观点。第一层采用最简单分类「小说 / 非小说」，两类对应独立上下文文件。Chat Pack 中该来源显眼、容易找到、默认不勾选、由用户主动选择。若实际规模超过合理上下文容量，可按书籍进一步展开选择——这是规模过大时的降级机制，不预先要求用户人工整理。
2. **R2｜建立独立的每周精读流程**：每周围绕最近阅读和划线进行一次精读。自动化负责整理近期读过什么、有哪些划线、哪些值得优先精读及推荐理由；用户本人在 WeRead 写下的批注、想法或主动输入属于高优先级候选。精读必须保留人的认知参与：针对重要内容至少形成「原始划线及来源 + 用户自己的理解/判断 + 可选行动」。AI 可辅助提问、关联和整理表达，但未经用户实际参与或确认的 AI 总结不得冒充用户认知。交互形态：**AI 给少量候选 → 用户跳过/展开/写判断 → 完成后生成精读文件**，而不是全部划线 → AI 自动长报告 → 用户被动阅读。用户必须可以跳过不值得处理的候选。
3. **R3｜精读成为新的独立输入源**：精读完成后生成独立的周度输入文件 `jingdu.md`，与既有 `weread.md` 明确分开。语义不同：weread 输入 = 本周读了什么、划了什么；jingdu 输入 = 用户对重要阅读内容进一步理解和判断后的结果。jingdu 作为 Learn-X 周一自动化的重要输入，**重要性/权重与 Flomo 同级**。
4. **R4｜不新建第二套长期认知资产体系**：精读职责止于生成高质量输入；之后是否形成长期核心认知资产，继续由 Learn-X 已有周一自动化及人工确认机制处理。

## 3. 非目标

首版不要求：

- 对历史全部划线进行价值蒸馏；
- 人工逐条筛选历史划线；
- 新建长期知识资产系统或另一套认知晋级体系；
- 自动把 AI 生成的观点写成用户认知；
- 复杂标签体系；
- 预先建立复杂语义检索产品；
- 改变现有 Learn-X 周一长期认知沉淀职责。

## 4. 已确认的关键裁决（2026-09-26）

1. **单一全量包**：存量归档始终只有一个全量规范包（小说/非小说两个文件），每次全量重建、幂等覆盖，不保留多个全量副本（历史靠 git）；体积预期几十至几百 KB，用户已确认备份体积无忧。
2. **刷新时机与精读同环节**：存量包全量重建纳入每周精读自动化，同一环节一起更新。
3. **精读交互在飞书文档**：Code X 周会话生成一个飞书文档，用户在飞书文档里跳过/展开/写判断；完成后告知 Code X 自动化「精读已完成」，自动化读回飞书文档生成 `jingdu.md`。
4. **分类机制**：以 WeRead `/book/info` 的 category 字段做确定性映射；歧义或缺失默认非小说；首次生成后人工核对歧义书单。
5. **Chat Pack 承载**：存量包以仓库 `.md` 文件进入 Chat Pack 上下文树，非推荐来源默认不勾选（沿用现有 `applyRecommendedSources` 行为），首版不改 UI。
6. **真实数据核验**：已授权用 Keychain 中的 WeRead API Key 做只读全量核验（实测数据范围、历史量、单文件规模、两包是否够用）。
7. **文件粒度按年（2026-09-26 用户裁决，替代 R1 的「按书籍展开」降级路径）**：实测全量 883,940 码点后，按书一文件（约 198 个）粒度过细、选择负担大；定为**年份为第一维度**——小说/非小说两目录下按年一文件，每本书整本归入「划线最多的年份」（不劈开书），目录内配按年列书目的 `_index.md` 让用户看得见每年有哪些书。R1 的交互基线（显眼、默认关闭、主动勾选）不变；「按书展开」不再作为文件结构，按年勾选即默认选择粒度。

## 5. 成功标准（验收矩阵）

| 成功标准或关键风险 | 验证方式与关键断言 | 预期证据 |
|---|---|---|
| R1 存量包可用 | 真实运行全量重建：两包生成、规模实测、来源语义完整（书名/作者/章节） | 两个 `.md` 文件 + manifest（书数、条数、字符数、生成时间、分类清单）；重复运行结果幂等 |
| R1 交互基线 | 本地 Chat Pack 上下文树出现「微信读书划线」独立分组，默认不勾选，可手动勾选；公开构建不含该目录 | 静态构建 local/public 对比 + 相关测试 |
| R1 降级路径 | 两包规模实测超限时的按书展开方案已在 execution-plan 预案化 | execution-plan 降级章节 |
| R2 精读保留人的加工 | 飞书文档候选 → 用户加工 → 读回生成 `jingdu.md`；未经用户确认的 AI 总结不进入 | `jingdu.md` 内容含用户写的理解/判断；状态侧车 `ready` |
| R3 来源契约 | `jingdu` 注册进 SOURCE_FILES；状态 `ready/empty/failed/unavailable` 语义与既有来源一致；Process Pack 总表纳入 | source-status 测试 + process:weekly 对含 jingdu 周目录的产物 |
| R3 权重与 Flomo 同级 | 周自动化阶段 2 验证清单与阶段 1 总表纳入 jingdu；缺失时显著提示 | weekly-automation SKILL.md 更新 + 流程试运行汇报 |
| R4 边界 | 精读产物止于 `03_input/weekly/`；不产生新的长期资产目录或晋级机制 | 仓库目录与代码审查 |
| 隐私边界 | 划线内容与 Key 不外发：Key 只从 Keychain 读取且不入日志/仓库；个人阅读数据不进公开构建 | 代码审查 + public 构建产物检查 + security scan |

## 6. 必要的剩余未知

- 完整历史划线的真实体积、小说/非小说两包是否已在可用规模内（Spike 首跑后回填 execution-plan）。
- 精读飞书文档的具体承载（每周新建独立文档 vs 固定文档分区）与写入授权范围，实施时按现有周记草稿授权模式单独确认。
- 精读候选每周条数上限等交互参数，以首周实际体验为准调优。

## 7. 停止条件

首版至少连续观察若干真实周次，重点验证两个现实结果：

- **周度精读**：用户是否实际完成认知加工，而不只是收到一份自动报告。
- **存量调用**：用户遇到真实问题时，是否实际勾选 WeRead 上下文，并认为其提供了有用的历史阅读背景。

若长期出现精读文件持续生成但用户基本不参与加工，或 WeRead 历史包因规模过大导致几乎无法实际加入上下文，应重新评审：届时优先调整交互、候选数量和选择粒度，而不是继续增加自动化复杂度。

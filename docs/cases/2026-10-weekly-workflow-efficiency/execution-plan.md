# Learn-X 分层智能恢复与问题修复记忆闭环

## 1. 目标与总体方案

保留已确认的三层恢复和提前交付方案，新增一个小型、流程专用的修复知识库：**记录真实问题、关键证据、尝试过的修法、验证结果和人工修复经验，下次优先复用，并推动反复出现的问题得到永久修复。**

这项增量没有新的方向性取舍。方案其余关键边界已覆盖；效果仍需通过实施和真实运行验证。

已确认的基础行为：

- 脚本管理并发、冷却、状态和校验；Agent 诊断问题、选择恢复动作及实施低风险小修。
- 日记有效就先生成草稿，其他来源缺口醒目提示。
- 阶段二仍需人工确认周记，再生成完整或有缺口的 Process Pack。
- 保留 05:00、07:00 两个固定时段；飞书 Build 使用已配置的周一 01:00 自动生成。
- AI 先观察原任务，符合严格条件时最多重发一次。
- 自动小补丁限一个根因、最多 3 个实现或规则文件、100 行有效增删，同时必须可验证、可回滚。

复杂度：需求中等（1）、系统高（2）、影响面高（2），合计 5，复杂档。

```mermaid
flowchart TD
    A[05:00 初次采集] --> B{日记有效}
    B -->|是| C[先生成草稿并提示缺口]
    B -->|否| D[恢复日记]
    A --> E[第一层：瞬态重试]
    E --> F[第二层：证据与已知恢复]
    F --> G[07:00 第三层：广域诊断与小修]
    D -->|成功| C
    C --> H[用户确认周记]
    H --> I[生成 Process Pack]
    I --> J[人工完成并审核 Chat Pack]
    J --> K[按原流程确认 Memory]
```

## 2. 三层恢复与来源处理

| 层级 | 处理方式 | 上限 |
|---|---|---|
| 第一层 | 网络、DNS、超时、HTTP 429/5xx 等瞬态问题，冷却后重跑原命令 | 每来源最多一次简单重试 |
| 第二层 | 对账、找已有产物、观察原任务、核对日期和版本、执行已知修复 | 每来源最多两种不同恢复动作 |
| 第三层 | 检查更广的调用链和上游生成逻辑，必要时实施受控小补丁 | 同周同根因最多一个补丁，随后验证性重采 |

非网络问题可以直接进入第二层。日记就绪时立即发出交付检查点，不能等待整个首次批次或冷却结束。

来源行为：

- **桌面 Build：** 每层重新核验产物，修正 `recheck-only` 不再检查的问题。生产根 Agent 提前记录自身线程、自动化、目标周和产物路径；额度恢复后最多续跑绑定的原线程一次，运行中只等待。
- **飞书 Build：** 只发现并核验其真实覆盖周，采用现有周一 01:00 自动生成配置；不调用 build-bot-log，不改旧报告标签补当前周。
- **AI：** 通过共享 Bridge 新增 `observe` 接口采回原会话结果，核验会话、runId、标记、归属及完整性。观察失败后，仅在归属明确、模板一致、没有有效本地结果、没有限流或生成中信号且未重发时，原子预占一次机会后重发。W41 已用过的机会保留，不再次发送。
- **WeRead：** 识别升级要求，核验并安装官方包，版本统一来自实际安装信息，然后重采；消除采集器硬编码漂移。
- **Health：** 修正 Markdown 生成入口，使有效本地报告及 Learn-X 导出独立于远端 Base 同步。分别报告本地生成和远端同步状态。
- **Flomo：** 复用有效快照，统一已确认的最多 10 条计数容差；身份、正文和稳定到底校验保留。
- **智慧之门：** Base 读取进入首次 CLI 批次，Flomo 导入作为独立增强步骤。
- **Core：** 正常无确认导出记为不可用，补查合法导出，不作为网络失败或用旧数据补齐。

    A --> C[现有执行器：锁、队列、预算]
    C --> D[来源采集器]
    A --> E[Codex 官方任务工具]
    E --> F[绑定的 Build 原线程]
    D --> G[Health-X / WeRead / 飞书 / Flomo]

## 3. 新增：问题修复记忆闭环

现有周诊断最多保留 500 条，主要记录运行流水；跨周检查又主要依赖粗粒度错误类别。新增两份本地文件即可，不引入数据库、向量检索、独立服务或新的调度：

- `state/recovery-incidents.jsonl`：追加保存关键问题、恢复动作、人工修复和验证事件，作为证据真源。
- `state/recovery-playbook.json`：从事件生成可查询的问题与修法索引，可以重建。

两份文件放在 weekly-automation Skill 目录下，明确忽略提交，不进入个人 Input、Memory 或学习上下文。

### 留存哪些信息

只保存异常和关键恢复节点，正常运行继续使用原有周诊断。

| 类别 | 留存内容 |
|---|---|
| 问题 | 来源、具体错误码或症状、发生阶段、首次与最近发生时间、问题指纹 |
| 层级 | 进入过哪些恢复层、每层尝试什么、最终在哪一层恢复 |
| 根因 | 已确认事实、待验证假设及支持证据，分别标记 |
| 修复 | 受控动作、前提、执行者、适用版本、成功及失败结果 |
| 验证 | 产物读回、覆盖周、状态、计数、相关哈希、测试摘要及证据引用 |
| 人工经验 | 用户明确说明的修复步骤、来源引用、核验状态 |
| 预防 | 永久修复候选、对应回归场景、修复版本和复发情况 |

不保存私人正文、健康数值、完整聊天、Prompt、凭据、原始响应、任意可执行命令或补丁正文。关键技术证据直接留存在事件中，不能仅指向可能被裁剪的周日志。

### 如何积累、复用和纠正

1. **同一故障跨三层使用同一个问题 ID。** 各层动作分别记录，避免一次故障被算成三次复发。相同 `unknown-failure` 不能直接认定为相同根因。
2. **诊断前查询最多三条适用经验。** 按来源、具体症状、阶段、相关版本及前提匹配；历史版本不适用时只作诊断参考。
3. **成功和失败都记录。** 区分“来源已恢复”“缺口已正确处置”“整体已交付”“根因已修复”，不把跳过来源计为恢复成功。
4. **人工修复先记录，再核验。** 用户明确说做过什么即可留下候选；产物读回或复现验证后升级为已验证经验，不推断未说明的操作。
5. **已验证经验不是新授权。** 只能选择当前允许的恢复动作；补丁仍需当轮风险审查，不能凭历史成功放宽门禁。
6. **复用失败时更新适用性。** 保留历史成功，追加失效或替代证据，停止优先推荐不再适用的修法。
7. **反复发生的问题推动永久修复。** 同一问题独立发生三次，或连续两周复发，生成一条去重的永久修复候选，附修改点和回归场景。根因修复落地、验证通过后标记预防已验证；未完成则保持待处理。
8. **下一轮做针对性预检。** 对已验证且属于安全只读检查的预防项，提前检查版本一致性、生产收据、日期映射等，减少同类问题再次发生。

索引记录发生次数、恢复耗时、经验复用成功与失败次数、人工介入及复发情况。根因确认与恢复验证分开：“重跑后成功”只能证明恢复，不一定证明根因。

```mermaid
flowchart TD
    A[三层恢复与人工修复] --> B[关键问题和验证事件]
    B --> C[修复知识索引]
    C --> D[下次诊断与针对性预检]
    D --> A
    B --> E{独立复发达到阈值}
    E -->|是| F[永久修复候选与回归场景]
    F --> G[根因修复落地并验证]
    G --> B
```

存储复用现有原子写入方式，加短锁及稳定事件 ID：先写事件，再更新索引。重复补写不重复计数；索引损坏可重建。记忆写入失败标为待补写，关键记录保留在原恢复收据中，继续生成内容；中间日志损坏时停止经验复用，不猜测修复事实。

首批整理本次 W40/W41 的关键案例：Flomo 容差、智慧之门连带等待、WeRead 升级、Health 导出、Build 发现与额度续跑、AI 读取失败，以及用户调整飞书 Build 时间。仅把有验证证据的结果标为已验证，其他保留候选或未解决状态。

## 4. 安全、状态与兼容

- 每次自动化使用一个 100 分钟共同截止时间，包含锁等待、冷却、Agent 调查、审查和测试；07:00 不重置历史次数。
- CLI 最多 3 路，浏览器单队列；成功来源和成功空结果不重跑。
- 保留来源状态契约，新增交付状态：完整生成、有缺口已生成、生成失败。
- 日记须真实有效且匹配目标周；阶段二须已确认周记。其他未验证来源排除并提示。
- 后到来源更新输入和缓存，不覆盖已有周记、人工编辑的 Pack 或 Output；刷新时列出差异。
- 自动小修必须有一手根因、适用范围、独立审查、原失败及相反情形验证。规模上限不是低风险证明。
- 应用前核对当前字节和哈希；回滚仅处理自己的改动且文件仍匹配补丁后哈希。并发修改时保留现场，不覆盖用户资产。
- 新诊断和知识查询接口采用加法升级；旧次数、AI 一次性标记和有效产物保留。记忆不替代当前来源、版本、身份和授权检查。

核心验收覆盖：

- 日记有效、其他来源失败时先交付；日记无效或周记未确认时保留相应门槛。

- WeRead 官方升级、版本一致、恶意包拒绝；Health 本地生成与 Base 失败分开。
- Flomo 缺口 0/1/10/11、Core 正常缺失、Wisdom 独立采集准确处理。
- 补丁超限、并发编辑、预算结束及人工内容保护。
- **同一故障跨三层只计一次；不同未知错误不误合并。**
- **人工声称修复但缺证据时保持候选；失效或版本不适用的经验不自动执行。**
- **记忆并发写入、重复补写、索引重建和写入失败不阻断交付。**
- **复发候选在根因修复与回归通过后能够关闭；历史经验不能扩大授权。**

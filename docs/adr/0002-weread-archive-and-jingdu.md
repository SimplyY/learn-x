# ADR 0002：WeRead 存量划线全量归档与周度精读输入源

- 状态：Accepted（2026-09-26；同日两次用户裁决迭代：聚合包 → 按书文件 → 年 × 分类文件定稿）
- 关联：[Requirement: weread-highlights](../requirements/weread-highlights.md) · [Case: weread-highlights](../cases/weread-highlights/case.md) · [Architecture Truth](../architecture.md)

## 背景

1. 用户全部 WeRead 公开划线目前只在每周 `weread.md` 周输入中出现（仅当周增量），历史划线在真实问题出现时无法被重新调用。
2. WeRead Agent Gateway（`/user/notebooks` 全量游标分页、`/book/bookmarklist` 单书全量划线、`/book/info` 含 `category`、`/review/list/mine` 想法）已在 `collect-weread-weekly.mjs` 中验证可用；Keychain 已存 API Key（`learn-x-weread-api-key`）。
3. Chat Pack 上下文树覆盖全仓 `.md`（`app/code/scripts/static-graph.mjs`），非推荐来源默认不勾选（`app/code/public/app.js` `applyRecommendedSources` 对未匹配文件置 `none`）。
4. 需求基线（已冻结）：存量不蒸馏；精读不另建长期资产体系；包过大时按书展开选择是需求自带的降级机制。

## 实测事实基线（Spike，2026-09-26，只读全量）

- 198 本有笔记的书、8,458 条划线、883,940 码点（UTF-8 实测 2,609,281 字节）；121 条想法仅 3,080 字符。
- 三重闭合校验：逐书实测划线数与 `noteCount` 198/198 全等；8,458 划线 + 121 想法 + 4 书签 = 8,583 = 服务端 `totalNoteCount`。
- API 行为：487 次串行调用（间隔 ≥250ms）0 错误、0 限流、0 重试，主采集 2.9 分钟——**串行足够，无需并发**。
- 分类（`/book/info` category）：小说类（一级含「小说」）23 本 66,603 字符；其余 175 本（含「文学-*」17 本与无分类 24 本，默认非小说）817,337 字符。
- 体积结论：聚合单文件小说包 ≈254KB、非小说包 ≈2.3–3.1MB——**聚合文件远超可用上下文，聚合方案不可行**；最大单书 56,713 码点（每本书均可整体进入上下文）。

## 决策

1. **存量归档 = 单一全量真源目录，年 × 分类文件、书整本不劈开**（2026-09-26 用户裁决，替代初版按书一文件方案）：
   ```text
   05_library/weread/
     fiction/<YYYY>.md        （小说：年文件，每年一文件，约 23 本全部划线的归属分布）
     nonfiction/<YYYY>.md     （非小说：年文件）
     _index.md                （按年列书目：书名｜作者｜分组｜划线数｜字数，纯元数据，让用户看见每年有哪些书）
     _manifest.json           （机器可读统计：分类分布、年度分布、逐书明细、闭合校验数）
   ```
   每本书全部划线归入「划线最多的年份」的年文件（并列取最近年；无有效日期的书归 `unknown.md` 并在 manifest 标注），书内按章节呈现全部划线；年文件内按最近划线时间降序排书。每周随精读自动化**全量重建、幂等覆盖**（含删除本轮 API 已不存在年份的旧文件）；不蒸馏、不删减；历史版本靠 git。
2. **两个目录 = 需求 R1 的「小说 / 非小说」两个入口**：Chat Pack 上下文树按目录分组天然呈现两入口（目录行自带文件数、文件行自带字数），用户按年勾选；聚合文件不生成（避免第二份全量副本）。
3. **分类确定性**：category 一级含「小说」→ fiction；其余（含「文学-*」与缺失）→ nonfiction 默认归属，分布与无分类书单写入 manifest 供一次性人工复核；扩展映射仅需改脚本内一个集合。
4. **承载方式**：仓库 `.md` 文件直接进入 Chat Pack 上下文树（显眼、默认关闭、主动勾选），首版不改 UI；`05_library/` 加入 `PUBLIC_PRIVATE_PREFIXES`（公开构建排除）并纳入每周备份根（划线是 WeRead 账号外唯一副本）。
5. **精读 = 新周输入源 `jingdu`**：交互在飞书文档（AI 候选 → 用户跳过/展开/写判断 → 口令确认 → 读回生成 `03_input/weekly/YYYY-Www/jingdu.md`）；写回走既有外部拥有者模式（写文件 + `npm run input:source-status`），已注册 `SOURCE_FILES`；权重与 Flomo 同级（阶段 1 固定总表 + 阶段 2 验证清单）。jingdu 不进入周六日「提前稿部分覆盖」豁免——它只有完成/未完成两态。
6. **不建第二资产体系**：`jingdu.md` 止于周输入；长期沉淀仍由既有周一自动化与人工确认机制处理。

## 被否备选

- **语义检索 / RAG over 全量划线**：非目标（需求明确不建检索产品），复杂度与维护面不满足最小充分。
- **AI 蒸馏历史划线为摘要库**：违反「存量不蒸馏」基线。
- **两聚合文件（fiction.md / nonfiction.md）**：实测非小说包 ≈3.1MB，无法整体进入任何上下文，交互不可用。
- **按书一文件（约 198 个文件）**：用户裁决粒度过细、选择负担大（「我选起来也很累」）；按年文件 + 书整本归主划线年取代。
- **API 并发拉取**：实测串行 2.9 分钟全量完成、零限流，并发属无必要复杂度。

## 后果与边界

- Chat Pack 树新增约 198 个文件（折叠于两个目录节点下，展开才见）；本地图体积增加可忽略。
- 文件名以书名清洗 + bookId 保证唯一稳定；书名清洗规则与截断在脚本内实现。
- 归档可由 API 全量重建（可再生产物），git + 备份双留存用于防 WeRead 账号侧数据丢失。
- 划线是个人阅读数据：公开构建必须排除；Key 只从 Keychain 读取，不入日志、参数或仓库。
- 精读飞书文档的创建与读取需用户身份（`--as user`），授权范围在实施时按周记草稿模式单独确认（见 Case Gate）。

# ADR 0001｜微信 Evidence Source 按需新鲜度与覆盖边界

- 状态：已确认（2026-09-24，用户裁决）
- Requirement：[wechat-evidence-source](../requirements/wechat-evidence-source.md)
- Case：[wechat-evidence-source](../cases/wechat-evidence-source/case.md)

## 要决定什么

微信 Evidence Source 的「新鲜」和「完整」如何定义与验收：

1. 新鲜度是否要求定时同步 / 全量索引追赶？
2. 「查询返回为空」与「账号里没有」如何区分？
3. 系统能否承诺微信历史绝对完整？

## 为什么必须现在决定

TraceMemo 2.4.0 公开 API 没有全账号时间窗流、分页游标或独立消息总数；Knowledge 搜索索引存在追赶状态；`sourceLatestAt` 只描述本机可读数据库，不能证明手机端已同步。这三点使「完整同步」在官方支持层面不可验证，若不先裁决，PoC 的验收标准会退化为健康检查自证，或把空结果误报为「没有聊天」。

## 候选方案与核心 trade-off

- **A 定时全量同步**：以定时 Knowledge 同步＋全量对账验收。官方不支持，实现即承诺不可验证的完整性；任何「通过」都是假阳性。否决。
- **B 按需可读＋搜索追赶状态（采用）**：已知会话与时间范围直读本机数据库（结果即真）；主题查询走 Knowledge 搜索，并强制返回 `coverage` / `indexLatestAt` 覆盖状态——覆盖未完成或追赶中时回答「暂无法确认」，不把空结果写成「没有聊天」。
- **C 只信健康检查**：以服务存活替代内容验证。以健康检查替代已知新增消息核对即自证，否决。

## 决策（含依据）

1. 新鲜度以「按需可读＋搜索追赶状态」验收：已知新增消息次日可在本机库查到，即为新鲜；不要求未获官方支持的定时 Knowledge 同步。
2. 绝对覆盖保持「未证实」：PoC 只能证明「已枚举的本机会话及抽检范围内未发现缺口」，不能证明微信账号全部历史完整。该未知标注在生成文件与 PoC 报告中，用户已选择标注后继续。
3. 周采集的完整性表述同样受限：对照 `conversation-overview` 计数，遇 200 条上限、计数不符或无法继续拆分时标记缺口并触发 `needs_review/failed`，禁止输出「完整」断言。
4. `messageRef` 只作可重新定位线索，不当永久链接或唯一去重键。

## 错判代价与可逆性

错判代价：若未来官方提供全账号对账能力，本决策会保留「未证实」标签——代价是措辞保守，不产生数据风险；反之若宣称完整而实际漏采，错误证据将进入 AI Chat、飞书备份并不可撤回。不对称风险支持本决策。

可逆性：高。验收口径是文档与输出格式层面的约定，不锁死实现；官方能力变化时可发新 ADR 替代，历史保留不覆盖。
